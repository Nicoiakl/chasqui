# x402 ↔ Nyx5

**x402** revives the HTTP status nobody ever used. A server answers `402 Payment Required` saying
what the resource costs, the client comes back with proof of payment, and the server answers `200`
with a settlement receipt. It is stewarded by the x402 Foundation under the Linux Foundation.

**Checked against**: x402 v2 (`x402Version: 2`), repository `x402-foundation/x402`, `main` at commit
`fdeda56` of 2026-09-09. Verified 2026-09-09.

Nyx5 speaks this. `src/puentes/x402.js` builds and reads the wire, and `test/x402.test.js` proves
the price a house announces is the price its ledger actually charges.

## Why this is conformant without a blockchain

The obvious objection is that x402 is a crypto payment standard and Nyx5 has no chain. That is not
what the specification says.

The core specification encourages non-blockchain networks to use the CAIP-2 identifier format, and
the repository already contains a scheme binding that settles in fiat: `cloudflare:402` uses `USD`
as the asset, a role constant instead of a wallet address as `payTo`, Ed25519 HTTP message
signatures for authentication, an empty transaction hash, stateless verification, and no external
facilitator at all.

Every one of those choices matches how Nyx5 already works. The precedent is in their repository,
not in our reading of it.

## The wire

| x402 v2 | Nyx5 | Verdict |
|---|---|---|
| `402` with the `PAYMENT-REQUIRED` header | A mailbox with a stamp policy, answering with its price | **equivalent** |
| `PAYMENT-SIGNATURE` header from the client | A signed envelope carrying a `stamp` field | **partial** — same role, different container. Ours is the envelope the protocol already signs |
| `PAYMENT-RESPONSE` header on success | The ledger entry id for the stamp that was charged | **equivalent** |
| `SettlementResponse.transaction` | The ledger entry id | **partial** — not a chain hash. A party to the entry can retrieve it from the ledger, signed by the house, and see the balanced double entry. Anyone else cannot: the journal is not public |
| `GET /supported` on a facilitator | `GET /x402/supported`, self-hosted | **equivalent** — the specification allows a resource server to host these itself |
| `POST /verify` and `POST /settle` | none | **missing here** — a house settles against its own ledger and delegates to nobody |
| The Bazaar discovery extension | The federated index and the agent directory | **partial** — both catalogue resources, neither can read the other |

## The objects

| x402 field | Nyx5 | Verdict |
|---|---|---|
| `scheme` | `exact` | **equivalent** |
| `network` | `nyx5:1` | **partial** — see the note below |
| `amount` (string, atomic units) | The price in tokens, as a string | **equivalent** |
| `asset` | `NYX` | **partial** — x402 expects a contract address or an ISO 4217 code, and this is neither |
| `payTo` | `agent@domain` | **partial** — x402 expects an address or a role constant; ours is an address in a different sense |
| `maxTimeoutSeconds` | 60 | **equivalent** |
| `extra.paymentFlow` | `authorization` or `upfront` | **equivalent** |
| `resource.url`, `mimeType`, `description` | The mailbox URL and its description | **equivalent** |
| `extensions` | none | **missing here** |
| Payment expiry | none in `PaymentRequirements`; it lives in the scheme payload | **partial** — a Nyx5 envelope has `expires`, which is the same idea in a different place |

### Why the network is `nyx5:1` and not the house

CAIP-2 requires `namespace:reference`, where the reference matches `[-_a-zA-Z0-9]{1,32}`. A dot is
not legal there, so `nyx5:nyx5.com` is not a CAIP-2 identifier and a conformant client would
reject it. The network is therefore the protocol, and the house travels in `payTo`, which is
already `agent@domain`.

The cost of that choice is stated plainly: two different houses look like the same network on the
wire. A payment on one house is not valid on another, and only `payTo` says which is which.

## What Nyx5 has that x402 does not

| Nyx5 | Verdict |
|---|---|
| A verifier that decides whether the delivery was real | **missing there** — x402 settles a payment, it does not judge a delivery |
| Bonds: a false claim forfeits a deposit | **missing there** |
| Reputation as a public ledger query | **missing there** |
| Chained mandates with a spending cap per link | **missing there** — the `upto` scheme caps one payment, not a delegation chain |
| A store-and-forward mailbox | **missing there** — x402 is request and response, both parties online |

The `escrow` payment flow in x402 comes closest: settle, deliver the resource, settle again. But
x402 does not say who decides that the second settle should happen, and Nyx5 is exactly that
decision.

## What we claim, and what we do not

**We claim**: a Nyx5 house speaks the x402 v2 HTTP transport. It answers `402` with a well-formed
`PAYMENT-REQUIRED`, it answers `200` with a `PAYMENT-RESPONSE` whose transaction id resolves in the
ledger, and it declares its capabilities at `/x402/supported`.

**We do not claim**: that an arbitrary x402 client can pay a Nyx5 house today. It cannot. Our asset
is a house token, not a contract address or a currency code, so a generic client can read the price
and will not know what to pay with. That is the same position `cloudflare:402` is in, where a payer
must have an account first. Conformant on the wire, and not universally interoperable. Those are
different claims and we make only the first.

**We also do not claim** any affiliation with the x402 Foundation. There is no conformance program,
no certification, and no official registry of implementations. Anyone who tells you they are
"x402 certified" is describing something that does not exist.

## Verified in production

On 2026-09-09, against the live house at nyx5.com: a mailbox charging 25 tokens announced
`"amount": "25"` in its `402`, refused an envelope with no stamp, accepted one with a stamp, and
returned a settlement whose transaction id resolves in the ledger to a balanced, house-signed
double entry of 25 out, 20 in and 5 of house fee.

## What is built

| Piece | Where |
|---|---|
| Wire module: build, parse, validate | `src/puentes/x402.js` |
| Capability declaration | `GET /x402/supported` |
| Price of delivery into a mailbox | `GET /x402/inbox/<name>` |
| `402` and settlement on delivery | `POST /inbound` response headers |
| Tests | `test/x402.test.js` |

Hard rules the tests hold to, because each one is a way to be silently wrong:

- `amount` is a string of atomic units. A number there is money in floating point.
- `network` matches the CAIP-2 grammar.
- `success`, `transaction` and `network` are always present in a settlement, even when the
  transaction id is empty.
- The price announced in the `402` equals the price the ledger charges. If the announcement and
  the ledger drift apart, the adapter is lying, and the test fails.

## Worth doing next

Submitting a scheme binding to `specs/schemes/` in the x402 repository would put Nyx5 in the
official specification directory. Their contribution template asks for seven things: commitment
format, verification rules, storage behaviour, double-spend prevention, expiry, redemption, and
trust model. All seven already exist here and are written down. This is the highest-value item and
it has not been done.

Third-party explorers list x402 resources, but they index on-chain networks and it is unverified
whether they accept one that has no chain.
